LIT Prompts

For help learning how to write prompts, see 50 Days of LIT Prompts. The first few exercises are a useful introduction, and later examples show more elaborate workflows.

This browser extension is a project of Suffolk University Law School's Legal Innovation & Technology (LIT) Lab. It was designed to help students explore prompt engineering and the operation of Large Language Models (LLMs), including their use in larger AI systems. Below you can create and save prompt templates for use by this extension. These templates can use data from your active browser window (e.g., selected text or the whole text of a webpage) as well as text input provided by you. They can also feed into each other, allowing one to create complex interactions. For example, you can make interactions that:

  • Summarize and ask questions of a webpage (e.g., What are the main conclusions of this article? What did so and so say about this or that?). sample
  • Draft an email reply responding to selected text. Then place it in your clipboard ready to paste into an email. sample
  • Define a selected word or phrase, appending the definition to a local Scratch Pad. sample
  • Save contents of Scratch Pad to a file. sample
  • Summarize and ask questions of text in the Scratch Pad (e.g., you could cut-and-paste content into the Scratch Pad when it's not available on a webpage). sample
  • Return a structured representation of a string's sentence structure (i.e., "diagram" a sentence in JSON). sample
  • Translate selected text from one language into another. Then draft a reply in the original language. sample
  • Flip a virtual coin and write a short poem based on the outcome. sample
  • Expand/build on selected text (i.e., have an LLM ask you questions to flesh out some text). sample
  • BS with the LLM of your choice. sample
Note: you can use the template feature without engaging an LLM to produce simple fill-in-the blank output (i.e., traditional form letters). sample

LLM API Integration

To run LLM templates/prompts, provide the complete API request endpoint below, an API key when the server requires one, and a model name on each LLM template. There is intentionally no provider selector: the endpoint path tells LIT Prompts which request format to use. This means local servers can live on localhost, a LAN IP address, or any other hostname without special configuration.

Endpoint examples and provider details

Endpoints ending in /responses use the OpenAI Responses API; endpoints ending in /messages use the native Anthropic Messages API; /chat/completions and unknown/legacy paths use the existing OpenAI-compatible Chat Completions format. Examples:

  • LM Studio / local OpenAI-compatible: http://localhost:1234/v1/chat/completions or, from another machine, something like http://192.168.1.50:1234/v1/chat/completions. The API key can usually be left blank. See Using LM Studio with LIT Prompts.
  • Google Gemini via OpenAI compatibility: https://generativelanguage.googleapis.com/v1beta/openai/chat/completions with a Gemini API key and Gemini model name. See Google documentation.
  • Anthropic via OpenAI compatibility: https://api.anthropic.com/v1/chat/completions with an Anthropic API key and Claude model name. This is convenient for ordinary prompts, but Anthropic's compatibility API ignores OpenAI's response_format. See Anthropic compatibility documentation.
  • Anthropic native (recommended when using JSON Schema): https://api.anthropic.com/v1/messages. LIT Prompts automatically switches headers, message formatting, response parsing, and structured-output formatting for this endpoint.
  • OpenAI: use https://api.openai.com/v1/chat/completions for Chat Completions or https://api.openai.com/v1/responses for Responses. Known model families get model-specific controls; unfamiliar future OpenAI model names keep optional reasoning/verbosity controls, with Auto omitting those fields. See Using OpenAI with LIT Prompts.
  • Other compatible servers: vLLM, reverse proxies, and other compatible endpoints can be entered directly. Generic endpoints use conservative compatibility mode and do not receive OpenAI-specific Reasoning Effort or Verbosity fields.

LLM requests are stopped automatically after this many seconds. Default: 120.

API Keys by Endpoint

Every endpoint, including the Default API Endpoint, has its API key here. Endpoint entries are retained even after prompts stop using them; entries that are neither the current default nor used by a prompt can be removed by clicking an × that will appear at the end of their input.

Endpoint and model selection are done on a prompt-by-prompt basis. A blank prompt Endpoint uses the Default API Endpoint above, and a blank Model uses the Default Model. API keys are stored separately by endpoint rather than inside prompt files, so changing a key does not require editing every prompt. Model names are passed through exactly as entered, so use the name expected by the endpoint you selected. API providers sometimes retire or rename models. If you use an API that lives somewhere other than on your computer (i.e., anything but a local server such as localhost or a machine you control on your LAN), you are sharing the contents of your prompts with the outside service. Check your API provider's privacy policy to see what they do with it.

Export to HTML

You can export runnable versions of your interactions to one of two HTML output types: (1) a page that replicates this extension's "popup," the window with buttons that appears when you click the extension; or (2) a page that replicates both the "popup" and a Scratch Pad. These outputs should run in any browser with access to the endpoint set above. The files will include a copy, not only of the endpoint, but also the API key listed above! If the endpoint or key above are blank, the user will be prompted to enter their own values when they hit an error. If you provide a password when prompted on export, your key will be encrypted and placed behind a password. However, anyone with that password will be able to access your key. Users will NOT be able to access text from any external page. The {{innerText}} and {{innerHTML}} variables will be set equal to {{scratch}}, and {{highlihghted}} will only work on text in the Scratch Pad. Additionally, they will not include links to edit the prompts or to a stand-along Scratch Pad. See the discussion of Prompt Templates below for more context.

The content of this textarea will be appended to your exports. HTML is allowed.

Prompt Templates

Author your own prompt templates below, or explore and contribute to our library of templates (pre-written template files you can upload here).

When crafting a template, use a mix of plain language and variable placeholders. Specifically, you can use double curly brackets to encase pre-defined variables and prompts for your user. If the text between the brackets matches one of our pre-defined variables, that section of text will be replaced with its content. For example, {{highlighted}} will be replaced by selected/highlighted text from the active tab when the popup is triggered, including text selected inside the LIT Prompting Scratch Pad or Templates & Settings page, {{innerText}} will be replaced by the text of your current page, {{innerHTML}} by its body HTML, and {{location}} by the current page URL. If the text within brackets isn't a pre-defined variable, like {{What is your name?}}, it will trigger a user prompt that echo's its content (e.g., "What is your name?"). After the user answers, their reply will replace this placeholder (i.e., {{What is your name?}}). A list of pre-defined variables can be found in the sample templates: Variables "random outcomes" and "time" and Variables "random outcomes" and "time". Both were included in the extension's default templates. Note: when looking at some templates, you will see comments between [# and #]. Such comments will not appear in the final prompts and are there to provide notes to template authors.

Advanced template settings

Post-run passthrough

Use the inputs after a template's name and body to set parameters. If you use the Post-run Behavior to send one template's output to another template, the first templat's output can be read by the second template via the {{passThrough}} variable. And if this value is valid JSON, you can access individual elements by calling specific keys (e.g., {{passThrough["key name"]}}. When using the "DYNAMIC" setting for Post-run Behavior the prompt found in {{passThrough["next"]}} will be triggered. To get a better hold on these behaviors, we recommend you read through this set of sample templates in order. You should also read this documenation on variable handeling.

Endpoint routing and model controls

Each prompt can optionally define its own endpoint; blank endpoints fall back to the Default API Endpoint. API keys are looked up by the effective endpoint and are never stored in downloaded prompt files. LIT Prompting detects the request protocol from that effective endpoint. Endpoints ending in /responses use OpenAI Responses; /messages uses native Anthropic Messages; /chat/completions and other endpoints keep the an OpenAI-compatible Chat shape. Temperature can be left blank for Auto/provider default. Max Output Tokens keeps a historical max_tokens key in prompt files but is translated to the parameter expected by the selected endpoint. Reasoning Effort and Verbosity are optional. For direct OpenAI endpoints, known model families get precise controls while unknown/future model names keep these newest controls. Auto omits these fields entirely. Generic compatible endpoints stay conservative and disable OpenAI-specific advanced fields. A capability status beneath each prompt's textarea explains the current behavior.

Structured JSON

When a template's JSON setting is set to Yes, a JSON Schema textarea appears. Paste a bare JSON Schema object there (for example, an object containing type, properties, and required). For Chat Completions endpoints, LIT Prompts wraps the schema in response_format.type = "json_schema"; for Responses endpoints it uses text.format; this works with servers such as LM Studio and Gemini's OpenAI-compatible endpoint when the selected model/server supports structured output. For an endpoint ending in /messages, LIT Prompts instead uses Anthropic's native output_config.format structured-output shape and reads the JSON from Claude's text content block. Anthropic's OpenAI-compatible /chat/completions endpoint ignores response_format, so use /v1/messages when you need schema enforcement with Claude. If JSON is enabled but the schema is blank, Chat Completions and Responses endpoints use the simpler json_object mode; native Anthropic receives a best-effort instruction to return only a JSON object because its Messages API has no equivalent schema-less json_object switch.

JavaScript Templates

Output Type can be set to JavaScript as well as Prompt or LLM. For a JavaScript template, the large template textarea contains JavaScript source code rather than prompt text. Endpoint, Model, Temperature, Max Output Tokens, Reasoning Effort, Verbosity, JSON, and JSON Schema do not apply and are disabled. Default Output, Post-run Behavior, and Hide Button continue to work normally.

JavaScript templates are transformation steps. The code runs in an isolated browser USER_SCRIPT world attached to the active webpage. It can use normal webpage APIs such as window, document, and fetch(), including reading or modifying the active page DOM, but it does not receive privileged WebExtension APIs. Network requests made by the code are subject to the normal rules of the page context, including CORS.

The code receives values as real JavaScript variables; do not put {{...}} template placeholders into JavaScript source. Available variables include passThrough, scratch, highlighted, innerText, innerHTML, location, nSelectedWords, nWordsOnPage, the existing date/time variables (including zero-indexed month, one-indexed month1, and padded month2d), and random-value variables such as coinFlip, d4, d6, d8, dPercent, d12, and d20. The JavaScript name dPercent corresponds to the normal prompt placeholder {{d%}}. scratch is parsed as JSON when possible and otherwise remains a string. passThrough keeps the type returned by the previous step.

JavaScript may be synchronous or asynchronous. It must explicitly return a value. That returned value becomes the new passThrough value and can be sent to another Prompt, LLM, or JavaScript template with Post-run Behavior. Objects and arrays remain structured values, so a later Prompt/LLM template can use expressions such as {{passThrough["name"]}}. For example:

return {
  selectedText: highlighted,
  wordCount: nSelectedWords,
  sourceTitle: document.title
};

A later Prompt or LLM template could then use values such as {{passThrough["selectedText"]}} and {{passThrough["wordCount"]}}, just like the built-in chained templates do.

If the JavaScript throws/rejects, returns undefined, or returns a value that cannot be represented as JSON-compatible data, the interaction stops and the error is displayed in the transcript rather than passing an unreliable value to the next template. JavaScript execution is available only in a compatible browser extension build; exported standalone HTML interactions do not have the extension userScripts API.
